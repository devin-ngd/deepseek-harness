# Agent Note：normal 重试策略按故障码免除次数上限

Status: implemented

[English](2026-11-16-retry-unbounded-codes.md) | 中文

## 问题

默认的 normal 重试策略对每种瞬态失败只重试五次、总窗口约十五秒，随后轮次以该失败结束。真实的网络中断以分钟计，因此在不稳定链路上的交互会话反复以 `TRANSPORT` 错误中止，只能等待手动续接。既有的 always 模式也不是可用答案：它不限次地重试所有失败码，包括 `QUOTA` 这类必须显现的终止性失败。

## 决定

normal 模式新增可选的 `unboundedCodes` 列表。列入的 code 必须本来就在 `retryableCodes` 中；命中的失败跳过 `maxRetries` 闸门，按同一有上限退避持续重试，直到成功、取消或释放。无上限 code 遇到超上限的提供方 `Retry-After` 时回退到有上限的本地退避而不委派，与 always 模式一致。解析后的策略只在该列表配置非空时携带它，持久化的 `policyKey` 也只在此刻追加它，因此既有配置的键字节不变，已钉住的固件保持有效。

默认策略不变。耐心程度是逐路由的部署选择，写在各提供方的 `retryPolicy` 中。

## 已考虑的替代方案

给 always 模式加 code 允许列表被否决：它会让未列入的 code 失去有界恢复，单次 `EMPTY_RESPONSE` 抖动在今天会重试、那样反而会直接终止轮次。提高默认预算仍然有界，更长的中断依然会被打断。轮次级自动续接也不纳入本次修复：请求级重试保持轮次不关闭，这正是失败会话所需要的行为。

## 影响

配置 `unboundedCodes: ['TRANSPORT']` 的路由不会因连接失败终止轮次；每次尝试都是持久且带倒计时可见的，由用户显式停止。聊天视图中超过声明上限的重试显示 `∞` 上限，该显示由事件自身推导。`TIMEOUT` 在发布姿态中保持有界，因为确定性的生成中途超时会在每次尝试都产生输入 token 计费。
