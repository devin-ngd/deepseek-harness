# MVP 数据通道 503 与代理突发额度

本次已取得手机数据通道的 HTTP 503，并在服务器现有 Nginx 上复现配置容量不足：同一个 key 的五个快速 HTTP 请求，`burst=2` 返回 `200,200,200,503,503`；最小修正 `burst=3` 返回 `200,200,200,200,503`。持续速率仍为每分钟五次。[真实 Nginx 证据](../evidence/nginx-burst-real-20261030.json)使用隔离 Unix socket、静态响应和相同限流模块，不是原手机 WebSocket 升级验收，没有新增公网监听或修改生产服务。

## 实机事实与判断

桌面仍为 rc2.19，原手机为 rc2.21、UID 20020297、PID 46498、窗口 609。h1 阶段桌面与手机最终调用均有回执，桌面当前面板提交已核验。过滤阶段显示手机控制挑战、身份校验、签名和房间回执通过，数据连接开始后未收到 HTTP 升级成功；固定失败事件为 `phone-data-socket-error code=200 http=503`。正常高级页面显示 `encrypted-handshake/timeout / cleanup-failed`，未进入会话或发送消息。数值详情保存在[本轮固定错误事件](../.build/rc221-mvp-20261030-h1/failure-details.json)，没有保存或打印原始业务日志。

实际站点两条路径共享以客户端地址为 key 的 `rate=5r/m`、`burst=2 nodelay`，并发上限为 4。双端各需一条控制连接和一条数据连接，合法的同来源连接共需四次快速升级；原配置在空桶情况下只容纳三次。[Nginx 官方说明](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)规定拒绝默认返回 503。结合实机 503 和真实模块对照，代理突发额度不足是有证据支持的原因；未记录本轮双端来源地址或 `$limit_req_status`，因此不能声称已排除所有其他 503 来源。修正后仍需用原双端完成一次实际连接及两条消息验收。

## 修复与候选

[代理提案](../standalone-relay/relay.nginx.conf.proposal)仅将两处 `burst=2` 改为 `burst=3`。每分钟五次、并发 4、660 秒读取超时、十分钟房间期限和原认证均保持。[四项回归](../tests/relay-upgrade-burst.test.mjs)覆盖旧配置拒绝第四次、新配置允许四次、第五次仍拒绝及其余限制；虚拟时间模型不冒充真实 Nginx。该文件被现有 `test:unit` 的测试通配入口覆盖。

[完整配置修订候选](../handoff/mvp-rc2.21-proxy-burst-20261030.zip)复用相同字节的未签名手机 HAP 和桌面插件，更新顶层、中继归档及公开工具归档中的全部 nginx 提案副本，并更新相应构建摘要；未重编译、重签名或安装客户端。所有归档 CRC、文件摘要和其余归档条目字节对照通过，[封存记录](../evidence/proxy-burst-candidate-20261030.json)记录完整变更。原 rc2.21 候选保持原字节。新候选未整包部署；下述实测仅临时应用代理修复，不能视为 MVP 已完成。

[独立产物冒烟](../evidence/proxy-burst-artifact-smoke-20261030.json)重新校验外层清单和 ZIP、HAP CRC、旧客户端载荷及所有归档条目的字节差异。解出的中继实际入口使用 `config.disabled.json` 运行后退出 0，两个公开维护工具的语法检查通过；没有使用已启用配置或替代原桌面进行消息验收。

## 收尾及执行限制

g1 阶段错误地在工具会话外发起后台桌面调用，驱动拒绝执行，双端最终提交和消息均为 0；该执行错误已保留。h1 改为显式等待，取到了上述 503。两次临时路由均已撤销，中继、nginx 和服务状态已独立恢复。h1 的停止回读确认原配对、UID、进程及窗口保留，没有重装、强停或清数据。

i1 准备了可恢复的代理修复脚本，但电脑再次锁屏，没有创建新路由或修改中继；预检驱动和 reader 已退出。公开 SDK 会启动另一个运行时，不能代替原桌面验收；没有用它操作其他会话。手机仅通过正常 Home／返回原应用刷新生命周期，前后 PID 和窗口相同，未强制停止。

用户要求完成前不让手机锁屏。现有 `power-shell timeout -o 1800000` 已返回成功，由独立 owner 定期续期；该 owner 在等待桌面解锁期间曾继续运行，后因原手机 USB Offline 退出；[当前路由修复和保活状态](route-restore-rc2.22.md)记录重连监督及后续恢复要求。它不修改解锁凭据，也不尝试解锁已锁定的设备。[旧锁屏记录](../evidence/mvp-desktop-blocked-20261030.json)保留为历史；用户解锁后的结果如下。


## 解锁后的实测与剩余问题

用户解锁后，代理修复已临时应用；桌面观察器补入有界、可取消的回读间隔，143 项离线检查通过。j1 数据通道完成 HTTP 升级后仍关闭，k1 在最终提交前出现手机路由不可用，原因未定，实际消息仍为 0，MVP 未完成。两轮路由均撤销，中继及 Nginx 原字节恢复、双端停止已独立核验；原配对和数据保留。该时刻手机保活 owner 仍运行，当前状态见[后续修复](route-restore-rc2.22.md)。[汇总证据](../evidence/mvp-proxy-jk-closeout-20261030.json)保留各轮结果与独立收尾。

j1 的四次连续桌面回读均早于异步面板更新，验证器提前报告提交未确认并触发停止。桌面适配器现在要求调用方提供 `pause(signal)`，只在仍未确认且还有观察额度时等待；截止仍由原协调器控制。虚拟时钟回归覆盖延迟 500 毫秒才更新的面板，以及等待期间取消后先排空再停止；[143 项整合检查](../evidence/desktop-submission-offline-1793374248322-6e94e3a0.json)全部通过。新等待逻辑尚未在完整实机最终提交中通过验收。

k1 的原手机签署及主机许可曾成功，随后最终准备首次读取已显示连接按钮禁用，正常页面显示无可用连接；没有双端最终提交、进入会话或覆盖草稿。手机约落后主机 5 秒，未发现遗留消息驱动，尚不能据此确定路由失效原因。下一步先复现并定位签署后路由状态变化，再安排同一流程的连接、输入框原值取证与两条消息；不继续盲目增加实机窗口。
