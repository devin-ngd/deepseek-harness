# Desktop identity storage and process-restart audit

This audit reads repository source, existing test/results and one known synthetic credential file's metadata/DACL. It does not read credential file contents, generate identities, run a model, operate the phone, start services, change ACLs or migrate credentials. Both requested areas still have engineering work; approval alone does not implement the missing storage or recovery paths.

## Current identity storage

[DesktopIdentitySigner](../desktop-plugin/src/identity.ts) stores harmony-desktop-identity/1 with publicSpki and base64url privatePkcs8 inside a credentials grant record. [The field entry](../replay-profile/src/field.ts) installs CredentialsLocal at the selected profile's .field-credentials.yaml. The [provider serializer](../../../packages/credentials/credentials-local/src/index.ts) writes grant payloads as YAML and uses atomic writes/locks. Base64url is an encoding, so the persisted PKCS8 is recoverable plaintext. Key-buffer clearing and releasing the live KeyObject do not encrypt the stored record or erase managed string copies.

The provider's assertOwnerOnly explicitly returns on Windows; its POSIX0600/0700 checks do not verify a Windows DACL. The field prompt and FIELD.md also describe inherited, unverified ACL protection. No protected-storage runtime provider is wired into this signer.

Only metadata was read from the existing synthetic test file first-use-wiring-world-ugEMqj/file-owner/fixture-credentials.yaml:472bytes, owner matches the current user, DACL protection is false and all9 rules are inherited Allow entries. They include AuthenticatedUsers with Modify and Users with ReadAndExecute, both containing ReadData. This file cannot be described as owner-only. No other-user read attempt was made, no real credential file was inspected, and these facts do not establish the ACL of a future real profile home.

A source search of credentials packages, desktop app and native code found no reusable runtime DPAPI/Credential Manager/safeStorage/keytar integration. The existing [upload credential launcher](../../../apps/desktop/scripts/upload-with-credentials.ps1) does use Windows DPAPI-backed CLIXML SecureString import, validates field types, filters a child environment and redacts output. Its [synthetic Windows tests](../../../apps/desktop/tests/upload-with-credentials.spec.ts) cover isolation and refusal of plaintext/blank/missing input. It is a release-upload command, not an identity-protection service; its COS-specific environment injection must not become the identity storage API. Reusable portions are the Windows-only subprocess/error/output discipline and synthetic qualification pattern.

## Current recovery support and limits

| Existing implementation/test | What it establishes | What it does not establish |
|---|---|---|
| [Profile admission journal](../desktop-plugin/src/journal.ts) | Durable submitting/accepted rows, exact desktop/profile marker, create/reopen distinction and refusal of missing/corrupt/wrong-owner state | Complete field process recovery or restoration of accepted work |
| [Executor reconciliation](../src/desktop-adapter.ts) and [canonical receipt lookup](../desktop-plugin/src/ports.ts) | Duplicate intent comparison, accepted receipts and uncertain outcomes; only the first claim dispatches, absent evidence remains unknown | Automatic retry of an uncertain command or task completion after a crash |
| [Admission tests](../tests/admission.test.mjs) | In-memory journal survives adapter replacement; no duplicate prompt and uncertain claim stays unknown | A second OS process reopening state from disk |
| [Phase32 production test](../integration/phase32-plugin.spec.ts) | Plugin dispose/reinstall in the same Context, durable journal reopen, rich receipt replay and one original prompt | Whole Context/Agent/Session destruction and restart in another process |
| [First-use signer test](../integration/first-use-refusals.spec.ts) | Two source Contexts reopen the same synthetic credential file and verify a signature without identity generation | Encrypted storage, Windows owner-only ACL or task recovery |
| [Phase42 journey](../integration/first-use-wiring.spec.ts) | Control-room reconnect, task receipt deduplication, rich history and native public-record owner reopen | Desktop process kill/restart with the same task/session |

The current field entry always mkdtemp's a new field-world, creates the fixed Session anew, reinstalls the four-response replay and selects journalMode:create. Its [strict configuration](../replay-profile/src/field-config.ts) exposes no stable world locator or create/reopen choice. DesktopFirstUse also requires the fixed Session already attached and requires another local enrollment confirmation after cold start. Therefore the field path cannot yet reopen an earlier desktop world/task.

Core cold Session infrastructure already exists: [inspection and ordinary Agent resume](../../../packages/api/session-controller/src/agent.ts), plus [history/follow](../../../packages/api/session-controller/src/history.ts). Reuse those owners rather than copying event reconstruction into the mobile plugin. Follow is not a purely passive cold read: its prepared-session path promotes the observation and can activate the ordinary Agent. Recovery tests must account for that activation and retain the replay-only dispatch block.

The saved phase42 result records5 passed tests. Those results were reviewed, not rerun in this audit. No existing reviewed test proves a two-process restart of this field entry preserving a mobile task through its admission/crash windows.

## Minimal implementation and synthetic validation plan

1. Add an explicitly selected identity-protection interface, a Windows provider using an OS-backed protection implementation and the DesktopIdentitySigner consumer. A protected successor record stores ciphertext and the public key, never plaintext privatePkcs8; its descriptor/parser fails on unsupported protection or decryption failure without plaintext fallback. Reuse existing atomic CredentialsLocal storage for the opaque owner payload rather than replacing every credential consumer. Keep the old record generation unchanged; document the persistence acknowledgement and explicit legacy policy before writing a successor. Do not migrate real identities. Any ACL check must report or refuse an unsuitable DACL; do not silently repair user ACLs.
2. Add an explicit stable field-world owner with create/reopen, exact profile/desktop/session identities and an independently versioned public manifest. Create refuses existing state; reopen refuses absent/corrupt/foreign state and never substitutes a fresh world. Reopen the canonical Session and admission domain through existing services. Keep local identity/enrollment/grant confirmation; reopening storage must not silently restore authorization. Use inspect/history for initial passive evidence and make later Agent activation explicit in the test policy.
3. Add two-process tests launched only through the supported isolated dsh replay profile. ProcessA writes synthetic state, reaches deterministic admission checkpoints, then exits or is killed; processB reopens the same explicit world. Cover crash before claim, after claim/before prompt, after canonical acceptance/before journal accept, and after completed-task persistence. Assert one original task request across processes, receipt/history consistency, unknown without evidence, unchanged rich terminal receipts, stale mount rejection and no duplicate effects. Recovery does not mean automatically rerunning a prompt after an unknown outcome; unfinished Agent continuation needs a separately tested explicit policy.
4. Cover protected-storage parser corruption/wrong public-key pairing/decryption failure/unsupported platform, duplicate alias and unknown write outcome, plus synthetic Windows protect/reopen and broad-DACL metadata refusal. Use only fixed fixture identities and disposable state; inspect persisted test bytes for absence of the fixture PKCS8 and verify a reopened signature. Do not use existing credential contents or modify existing ACLs. Preserve zero real calls/uploads, no phone/broker connection and fixed replay budgets in every child process.

Recommended order is protected identity storage first, then stable field-world reopen and cross-process failure injection. The present plaintext provider and missing field reopen remain explicit implementation gaps until those checks pass.
