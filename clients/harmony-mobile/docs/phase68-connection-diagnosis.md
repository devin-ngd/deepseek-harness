# Connection diagnosis and inactive candidates

This reference describes the offline diagnosis after the [revoked field window](phase67-field-closeout.md). No field grant was created or renewed, no relay was activated, and no phone installation or key operation was performed. The existing grant tombstone remains the authority for that completed window.

## Confirmed compatibility failure

The original control and data upgrade handlers reject every Origin header. OpenHarmony NetworkKit supplies a default origin when creating its libwebsockets connection; the library writes a scheme-qualified Origin. The installed API26 declaration has no option to omit it. The preserved nginx proposal does not strip it. The deterministic same-pair test gets 101 without Origin and 403 with the canonical HTTPS Origin, before any broker signature or room allocation. This is a confirmed client/server incompatibility at the control HTTP upgrade stage. See the [NetworkKit implementation](https://raw.githubusercontent.com/openharmony/communication_netstack/master/frameworks/js/napi/websocket/websocket_exec/src/websocket_exec.cpp), [earlier release implementation](https://raw.githubusercontent.com/openharmony/communication_netstack/OpenHarmony-6.1-Release/frameworks/js/napi/websocket/websocket_exec/src/websocket_exec.cpp), and [Origin serialization](https://raw.githubusercontent.com/openharmony/third_party_libwebsockets/master/lib/roles/http/client/client-http.c).

The first fault in the physical attempt is not trace-proven: no original upgrade headers or HTTP refusal status were captured. Empty sampled backend connections and the absent catalogue do not distinguish DNS/TLS, HTTP upgrade or an earlier desktop failure. The phone binary's platform implementation has not been matched to the upstream source. The synthetic failure therefore establishes an unavoidable incompatibility for the examined NetworkKit behavior, not an assertion that every earlier layer succeeded on that device.

NetworkKit's successful connect return can precede the open event. The upstream receive callback supplies undefined in its error position on success, so the hypothesis that the existing truthiness check rejects every successful message is unsupported. Two tests exercise the actual ETS socket owner with early dial completion and both error-callback layouts. Diagnostic output now distinguishes dial return, HTTP upgrade, first control/data frame and authentication deadline. It records only bounded stage names, integer native codes and validated HTTP status numbers; error messages, headers and capabilities are omitted.

## Minimal candidate and retained authority

The [relay README](../standalone-relay/README.md) owns nativeOrigin configuration. The default remains deny. Explicit networkkit-v1 admits only the configured canonical HTTPS Origin for a phone request with the existing required custom routing headers. Cookies, browser fetch metadata, other hosts, noncanonical origins, desktop origins, unknown pairs and incorrect capabilities remain refused. Browser WebSocket cannot supply those native custom headers. Both original signing identities, fresh broker proofs, one-use room capability, pinned E2E and original desktop grant checks remain required. This candidate has not been deployed.

The native candidate displays terminal connection failure separately and disables repeated Connect activation after that terminal state. Existing public records remain unchanged on expiry or rejection. Tests confirm that a new candidate cannot implicitly replace an expired saved record, and that a local revocation tombstone survives reopen. Explicit replacement of an expired pairing with a newly approved grant is still unimplemented. The next field attempt must first resolve that flow while preserving the old record, desktop revocation epoch and relay journal; clearing data or resetting identity/history is not a recovery method.

## Independent proxy capacity finding

The preserved deployed proposal hash is 3d3f43d11bf6496f6555606812bd4d72c4c54a2f4fcfc3ac9d9a08ca908284b2. Its two upgrade locations share a 5-per-minute zone with burst 2 and a four-connection cap. If both endpoints share one public address, initial control plus data requires four near-simultaneous upgrades; an empty bucket permits only three. This conditional capacity defect can reject a later request independently of Origin. The candidate changes only both burst values to 3, retaining the rate and connection cap. The executed capacity check rejects the predecessor and accepts that declared initial plan. It is not a real nginx execution test; the field endpoints' public addresses and a 503 response were not observed. Failed rapid recovery can still hit rate limits. See [nginx admission semantics](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html#limit_req).

## Validation and delivery

The focused source suite passes 40 tests: default and NetworkKit-origin complete fixed four-response journeys, rich action, stream, reconnection without repeated dispatch, cancellation, upgrade refusal, terminal state and retained public trust. Strict TypeScript checks pass for 152 lab/integration modules. Twelve node checks pass for native layout/actions, marker redaction, both native error-callback layouts and initial proxy capacity. Matching built relay/public-maintenance smokes verify inert import, disabled startup, exact proposal output, exclusive-file preservation and no-TTY initialization refusal. No live model or installed device is used by those tests.

Candidate identifiers, compile evidence and exact hashes are recorded in the final candidate evidence. The first unsigned diagnostic HAP is retained separately from subsequent compile attempts; only the latest successfully sealed candidate is eligible for review. Signing, phone installation, relay/server or nginx updates, replacement public trust and another timed field grant all remain separate approval decisions. ArkTS compilation, SDK substitution and loopback success establish none of native NetworkKit TLS, actual ArkWeb execution, Linux candidate execution or final device acceptance.
