# Phase40: public revocation and paired connection owners

The isolated client now has a public-only durable revocation writer, a shared control/data/E2E owner, actual ArkTS WS/HUKS adapters and an optional desktop plugin lifecycle provider. Import and default config remain inert. The installed DSH, server, phone and existing release archives were not changed. This is a verified development checkpoint, not a production activation recommendation.

## Verified scope

`PublicTrustStore` serializes append-only public snapshots and a separate digest/generation head under an exclusive lock. Reopen retains revoked pairs; missing, torn, corrupt, mismatched or unknown-write state refuses startup. Enabled CLI brokers require explicit existing public state before listening. No CLI/HTTP enrollment or automatic repair is available. Both journals synchronize before acknowledgment, and applicable directory synchronization includes lock creation/removal. Windows tests use real temporary file writes/sync and a substituted directory-sync port. Restoring both journals to the same old backup is not detectable without an independent trusted anchor; Linux filesystem and power-loss behavior remain unqualified.

`PairedRelayEndpoint` is shared by the native facade and desktop provider. Each room requires both fresh role proofs and new transient E2E material. The original locally stored desktop grant is proved again on the new pinned binding. Native `NativePairedConnectionOwner` uses an existing HUKS alias and actual NetworkKit WS adapter; it does not create an identity or expose a signer to ArkWeb guests. Background/destruction closes all active paired owners; foreground does not automatically reconnect. Desktop `relayEnabled` defaults false and requires a local provider before mounting. Request results remain bound to their original connection, and mount/unload failures close sockets/listeners/timers and settle pending operations. Bounded control sends retain the transport's live buffered amount.

The actual ETS owner was tested against synthetic SDK implementations and an ephemeral loopback relay connected to the current source desktop plugin/Gateway/SessionController. The flow proves both roles, validates the original read-only grant, retrieves scoped metadata, streams a Session reset, rejects task submission without calling prompt/model, obtains a fresh room after data loss, reauthenticates, and closes on native background/plugin unload. This is not actual HUKS, TLS, ArkWeb, installed desktop or phone execution. Lost control transport requires a new explicit connection; no automatic task retry or general host execution bridge exists.

Final checks: 119 synthetic/source tests passed (26 new plus 93 preceding cases; one old evidence-writing case deliberately excluded), 131 modules passed strict TypeScript 6.0.3, six shipped-ESM tests passed, and the isolated permission-free unsigned project compiled with installed DevEco 26.0.0.851 / SDK 26.0.0.105 API26. The compile target imports the owner but does not activate it. SDK warnings for permission/device availability remain relevant to future activation. ## Remaining work and permission

- Software: connect the production native trusted UI's explicit pairing/connect decision to its public record and existing-key owner; bind the actual desktop local confirmation/provider/identity acquisition to the original grant owner. The cold-start grant policy still denies until local confirmation. These cannot be described as deployment-only blockers.
- Software: explicit control-loss reconnect/backoff and journal/cursor recovery need product composition and tests; full task/cancel/approval/rich form/query/action/revision/draft flows need the paired owner path. Existing earlier fixtures do not establish this native paired end-to-end behavior.
- Requires corresponding approval: initialize real public pins/storage, use real existing identity credentials, select/install the optional desktop plugin or restart DSH, deploy relay/service/nginx/DNS/TLS or open network access. No approval was inferred from silence.
- Requires corresponding approval and actual evidence: phone signing/account/permissions/install; actual device API/HUKS key protection/TLS and ArkWeb rich interaction; Linux filesystem/power-loss/proxy qualification; phone task → actual desktop execution → correct-session stream/rich result, including reconnect with no duplicate execution. Mate90 Pro Max / HarmonyOS7 is known; actual API and signatures are unmeasured. Real model tests remain forbidden in this checkpoint.

No committed Session format or grant generation changed. The new public trust journal is a private, explicitly initialized format. Unknown writes retain the lock and require separately approved diagnosis rather than automatic recovery. Source rollback preimages and additions are included in the incremental archive; restore only those client files and preserve prior archives and unrelated dirty work.
