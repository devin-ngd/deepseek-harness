# Relay startup and lock recovery

The relay reports a fixed startup stage and reason without exception text, configuration values, keys or routing records. The stages are `config`, `public-trust`, `device-routes`, `initialization` and `listener`. A locked or unknown state still fails closed; inspect the stage and the state files before changing anything.

`HARMONY_RELAY_LOCAL_LOCK_RECOVERY=1` opts into recovery only on Linux when the state directory is private to one host and the boot ID and process namespace identify every possible writer. Never enable it on shared or replicated storage, or when another host/container with an independent PID namespace can write the same state. With the option disabled, existing exclusive-lock behavior is unchanged.

The new lock records its boot ID, owner PID and clean/dirty phase. Before appending either state journal it durably marks the lock dirty, and retains that phase until normal close removes the lock, even after a successful write. This conservatively preserves uncertainty if a process dies after committing but before its caller receives the result. An active owner, dirty lock, unknown/legacy lock or competing recovery is refused. A clean lock whose owner has exited can be archived and acquired by one contender; existing journal, head, signatures and revocation checks still run before listening. A reused PID can conservatively block recovery. Incomplete recovery or an unrecognized old lock may require an operator to investigate; never simply remove an unknown or dirty lock.

The first migration from a running older version requires a normal stop that removes its legacy empty locks. Preserve the original binary, service configuration, journal and head; if the normal stop leaves locks or writes in an unknown state, stop and investigate rather than overriding them. Replacing the running relay drops its current ephemeral rooms and requires endpoints to reconnect. A rollback to an older binary likewise requires a clean stop to remove the new-format locks; older versions will not recover them automatically.

The Linux test runner `node scripts/check-relay-crash-recovery.mjs` builds isolated bundles and uses synthetic temporary journals. It exercises active owners, crash recovery, concurrency, dirty and legacy locks, public journal revocation persistence, route reopening, interrupted writes and redacted diagnostics. It does not contact the real relay, modify pairing, or establish phone acceptance.

On dhome, the 2026-11-06 deployment uses `/home/devin/harmony-relay/candidates/rc2.30-lock-recovery-20261106-v2/server.mjs` and the separate systemd override `90-crash-recovery.conf`. The prior `rc2.30` binary, paired configuration and `80-paired-devices.conf` remain in place. The four existing journal/head hashes matched before and after the switch; the listener and unauthenticated 403 were checked. Real phone reconnection and power-loss behavior were not checked. To roll back, first stop the relay cleanly and verify both state locks disappeared; only then remove this override, reload systemd and start the prior unit. If locks remain, preserve them and investigate instead of forcing rollback.
